OSSM system architecture

Guest access and device authority are separate processes. The guest web service handles the UI; the private admin service owns sessions, safety policy and every device write.

01   Deployment & connections 02   Control enforcement
01

Deployment & connections

Two independently running services on one computer. Remote access ends at guest web; local administration has its own private entry point.

02

Control enforcement

Guest web filters input early. Admin independently decides whether each request can reach the device; its controller checks again at execution.

What these boundaries do — and do not — guarantee

No accounts. Local operator and guest access use separate temporary capabilities. Creating a session link does not approve a guest, arm the device or start motion.

No direct guest control. Guest web cannot invoke admin-management methods or obtain device permissions. Admin still constrains input from a compromised guest process that possesses a valid guest capability.

Physical overrides take precedence. Device parameter changes not explained by an owned command trigger lockout and Stop. Expected command readback is distinguished from external changes. The physical remote's detectability and stopping behavior must be demonstrated on the selected firmware.

Physical release remains gated. Admin, OS or bridge failure can prevent a software Stop. Independent stopping on the selected hardware/firmware must be demonstrated; a completed write or readback is not physical stop confirmation.
